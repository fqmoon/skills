# Evolve

Evolve 是一个**持续交互式的软件演化校对模式**。

它的核心目标是：

> **通过项目的真实实现、测试和设计文档，重新认识 Intent，并维护长期有效的设计决策与行为约束。**

Evolve 不只是整理历史知识，也不只是检查文档与代码是否一致。

软件在持续开发中会发生变化。新的实现、测试和用户反馈，可能揭示出过去没有明确表达的 Intent，也可能推翻原有的设计判断。

Evolve 负责识别这些变化，判断哪些设计理由与行为要求仍然有效，并将值得长期保留的认识维护到项目中。

# Mode

Evolve 是持续生效的 Mode，而不是一次性 Action。

用户通过 `/evolve` 进入模式，并指定需要校对的范围或方向，例如：

- `/evolve 检查 Layer 生命周期`
- `/evolve 最近两周的开发变化`
- `/evolve 校对 Shader 参数系统的设计`
- `/evolve 重点检查持久化与恢复行为`

范围可以是模块、功能、架构主题、时间区间或其他自然语言描述。

如果用户没有提供任何范围或方向，且当前上下文也无法确定，应要求用户指定，不擅自对整个项目进行无限范围的校对。

进入 Evolve 后：

- 当前范围或方向在后续对话中持续有效；
- 后续用户消息默认用于继续当前校对工作；
- 用户可以随时调整范围、提出质疑或改变校对方向；
- Agent 应主动调查、判断、提出建议并推进已授权的修改；
- 单次调查或修改完成不意味着退出模式；
- 只有用户明确要求退出，例如 `/evolve off`，才终止模式。

Evolve 不维护独立的版本标记、Checkpoint 或模式状态文件。

# 核心认知模型

Evolve 以 **Intent、Decision、Behavior、Reality** 四个视角理解项目。

## Intent

为什么这样设计？真正希望获得或保留什么？发生取舍时，什么更重要？

Intent 不一定已经被明确写出，也可能隐藏在现有实现、测试和历史变化中。

## Decision

项目已经作出了什么重要设计决策？为什么选择这些方案？当时排除了哪些替代方案？这些理由现在是否仍然成立？

Decision 不等同于永久约束。历史决策可以被修订或推翻。

## Behavior

项目目前体现了哪些可观察行为和不变量？哪些行为被测试保护？这些保护是否仍然合理？

测试通过不等于行为要求有效，测试失败也不自动意味着代码错误。

## Reality

当前代码、实际运行结果、数据流、架构以及外部行为究竟是什么？

Reality 是调查依据，但现有事实不自动成为应当保留的设计要求。

四者是分析视角，不是固定执行步骤。

# 调查与 Intent 重建

Evolve 应根据用户指定的范围，自主寻找相关证据。

优先调查：

- **ADR：** 已有设计决策、理由、约束与历史取舍；
- **Test / Fixture：** 被保护的行为、场景、边界与不变量；
- **Code：** 当前实现、架构、数据流与实际行为；
- **项目文档：** 项目真正使用的需求、设计、接口、使用说明等；
- **History / Change：** 必要时调查历史提交及变化原因。

不要为了完整性无边界扫描整个项目。

## 正向校对

根据已有 Intent 和 Decision，检查当前实现、测试与文档是否仍然体现原来的重要目标和约束。

重点识别：

- 原有设计决策是否仍然成立；
- 当前实现是否已经改变其前提；
- 重要行为是否缺少有效测试；
- 文档是否仍然准确；
- 已有测试是否保护了不再有效的行为。

## 反向发现

从当前 Code、Test 和项目历史出发，主动寻找尚未明确表达的 Intent。

例如：

- 新增的一组 Fixture 可能揭示了新的行为约束；
- 多次重构后保留下来的某种性质，可能体现了重要设计原则；
- 新实现可能使原来的 ADR 不再成立；
- 多个测试共同保护的行为，可能值得上升为显式设计决策；
- 当前文档缺失的设计理由，可能已经体现在代码与测试中。

反向重建得到的是**候选 Intent**。

不要仅因为某个行为存在、某项测试通过，便认定它是用户真正希望保留的要求。

应结合现有证据形成合理解释，对重要且无法确定的判断交由用户裁决。

# 有效性校对

Evolve 应主动检查长期资产与当前 Reality 之间的关系。

重点包括：

- **Missing：** 重要设计决策或行为约束尚未得到记录或测试保护；
- **Outdated：** 现有决策、文档或测试已经过时；
- **Contradictory：** 不同资产之间存在冲突；
- **Accidental：** 偶然实现、历史 Bug 或临时方案被误认为长期约束；
- **Redundant：** 重复、无价值或过度依赖实现细节的约束；
- **Preserved：** 现有决策和行为约束仍然有效，应继续保留。

不要求机械地输出上述分类。

尤其不要把一致性本身当作目标。ADR、Test 和 Code 即使完全一致，也可能建立在过时或错误的前提上。

# Test 与回归验证

Evolve 应主动使用项目现有的测试能力验证判断。

根据调查范围，合理选择：

- 相关单元测试与集成测试；
- 代表性的 Fixture；
- 跨组件行为测试；
- 属性测试与边界测试；
- 必要的端到端测试或其他运行验证。

原则上，应在需要时建立修改前的测试基线，并在修改后执行相关回归验证。

不要求为了校对一个局部问题而机械运行所有测试。

## 测试失败的处理

测试失败不能直接等同于代码需要修复。

应根据 Code、ADR、Change 和实际行为调查原因，区分：

- 代码违反了仍然有效的约束；
- 测试断言已经过时；
- 原有设计决策已经失效；
- 测试环境或测试本身存在问题；
- 当前需求与历史约束存在尚未裁决的冲突。

修改既有测试断言时，必须能够说明其原有要求为什么不再有效。

不能为了通过测试而降低行为约束，也不能未经判断就把当前实现输出固定为新的 Golden Baseline。

如果测试无法执行，应明确说明原因以及尚未得到验证的结论，不得声称回归已经通过。

# 主动性与交互

Evolve 应具有较高主动性，但不能替代用户决定重要的设计意图。

Agent 默认负责：

- 自主调查相关项目资产；
- 主动发现隐含 Intent 与潜在冲突；
- 判断哪些发现具有长期价值；
- 提出具体、可执行的默认修改方案；
- 解释推荐保留、修订、淘汰或新增的理由；
- 根据用户反馈实施修改；
- 自动执行必要的测试与回归验证。

**不要把候选问题清单直接交给用户，让用户代替 Agent 完成分析。**

当存在多个合理解释时，Agent 应先形成自己的推荐判断，说明主要依据与重要取舍。

用户主要负责：

- 判断重要 Intent 是否符合实际目标；
- 裁决存在实质分歧的设计方向；
- 授权重要的长期约束变化；
- 否决或调整 Agent 的默认提议。

不必对普通调查步骤、测试命令、局部文字调整和无关紧要的实现细节逐项询问。

对于多项相关建议，可以集中展示默认方案，允许用户整体接受或局部否决。

在重要语义尚未确认之前，不应擅自将推测出的 Intent 固化为长期约束。

# 长期资产维护

Evolve 的维护对象是**项目真正使用的长期资产**，而不是固定的一组文件或目录。

重点是 ADR 与 Test，但不机械限定于此。

根据实际项目结构，可以维护：

- ADR：设计 Intent、Decision、Rationale、Alternatives、Constraints；
- Test / Fixture：值得长期保护的行为及其可执行验证；
- 架构与设计文档：当前有效的系统结构和重要设计原则；
- API / Protocol 文档：接口契约及兼容性要求；
- README / 用户文档：实际能力、使用方式和对外行为承诺；
- 其他项目已有的长期文档。

应优先遵循项目已有的文档体系，不为了 Evolve 额外创造文档层级。

ADR 是设计决策的优先载体，但不应把所有行为、实现细节和使用说明都转换成 ADR。

## 维护方式

Evolve 不只负责新增内容，也负责：

- 修订已经变化的设计决策；
- 明确取代失效的历史决定；
- 补充遗漏的重要理由；
- 更新不再准确的文档；
- 增加值得长期保护的 Fixture；
- 修改已经失效的测试断言；
- 清理冗余或误导性的长期约束。

**维护的目标是提高长期资产的有效性和信息密度，而不是增加文档或测试数量。**

如果经过校对，没有发现值得修改的内容，可以明确建议保持现状。

# 修改权限与边界

Evolve 可以自主调查、运行测试和准备修改方案。

对于影响重要 Intent、设计决策或既有行为契约的修改，应先给出默认建议，经用户确认后实施。

用户确认总体方案后，Agent 应自主完成必要的文档与测试修改，不重复请求没有必要的局部确认。

Evolve 默认不负责修改产品代码。

如果发现当前实现违反仍然有效的设计或行为要求，应报告实现问题及推荐处置，而不是擅自展开大规模重构。

用户可以明确授权相关代码修改，但不得因此自动扩大整个 Evolve 范围。

# 与其他 Skills 的关系

## Impact

`impact` 面向拟议 Change，调查其对现有代码、决策和行为约束的影响。

`evolve` 面向当前项目状态，校对这些决策与约束本身是否仍然有效。

两者可以互相提供信息，但不构成固定调用链。

## Regress

`regress` 是单次任务后的语义回归，通过独立重建最终 Reality 中体现的 Intent，与原始 Intent 进行比较。

`evolve` 是持续交互式的长期演化校对，允许直接参考 ADR、History、Test 和已知设计意图，并实际维护长期资产。

Evolve 不需要模拟 Regress 的 Blind Reconstruction，也不应替代它。

## Intent / Gate / Impl

Evolve 可以使用这些认知模型区分：

- Intent：为什么做，什么更重要；
- Gate：哪些结果不可接受；
- Impl：当前采取的具体实现手段。

尤其不能因为某个 Impl 已经存在，或者被历史 ADR 记录，就自动认为它属于不可改变的 Gate。

# 输出与持续推进

Evolve 的汇报应优先展示会影响用户判断的内容：

- 当前识别出的主要 Intent；
- 已确认的重要设计或行为变化；
- 发现的长期约束缺口与冲突；
- Agent 推荐的修改方案及理由；
- 实际执行的测试与验证结果；
- 真正需要用户裁决的问题。

不要默认输出完整调查日志，也不要求每轮使用固定报告模板。

当某个范围的校对已经完成，应总结实际修改、仍然有效的约束和未解决问题。

完成当前范围后，**保持 Evolve Mode**。可以继续响应用户的新方向，不因一次校对完成而自动退出，也不为了维持模式而强行寻找新问题。

# 不要做什么

- 不要在没有用户指定范围或方向时进行全项目无边界调查；
- 不要创建 Evolve 专用版本、Checkpoint 或状态文件；
- 不要把 Evolve 变成自动生成 ADR 的流水线；
- 不要仅凭 Code 或 Test 的存在推断确定的 Intent；
- 不要把历史 ADR 当作不可推翻的权威；
- 不要把当前实现自动升级为长期约束；
- 不要为了保持一致而机械修改文档或测试；
- 不要为了测试全绿而删除有效断言；
- 不要把全部候选判断转交给用户；
- 不要在未经授权时改变重要设计语义；
- 不要默认展开产品代码重构；
- 不要因为一次调查或修改完成就退出模式；
- 不要以沉淀数量衡量 Evolve 的成果。

# 核心原则

> **从 ADR、Test、Code 和项目文档中重新认识 Intent；通过真实行为验证既有约束，通过持续交互校正长期设计判断。**

> **Agent 主动调查、提出默认方案并完成验证；用户负责重要语义的裁决，而不是负责每一步调查。**

> **维护项目实际使用的长期资产，重点关注 ADR 与 Test；保留仍然有效的知识，修订已经变化的认识，淘汰失效的历史约束。**

> **Evolve 不是让软件保持不变，而是让软件在不断变化中，仍然清楚自己为什么成为现在的样子。**
