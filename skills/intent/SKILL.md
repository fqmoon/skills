# Intent

Intent 描述当前决策背后的**方向与理由**。

它回答的不是：

> 具体怎么实现？

而是：

> 为什么要这样做？真正想获得什么？如果发生冲突，什么更重要？

Intent 用来帮助 Agent 在多个看似合理的方案之间做判断，并在实现细节变化时保持总体方向不漂移。

# 什么属于 Intent

Intent 通常包括：

- 最终希望达成的方向；
- 设计意图；
- 优先级；
- 取舍偏好；
- 希望保留、强化或削弱的性质；
- 为什么当前问题值得解决；
- 明确的非目标；
- 当多个目标冲突时，应该优先保什么。

例如：

> 优先保持全局 SDF 模型简单，即使这意味着放弃部分传统笔刷属性。

这是 Intent。

它描述的是方向和取舍，而不是实现手段。

# 什么不属于 Intent

以下内容通常不属于 Intent：

- 具体算法；
- 数据结构；
- class / module 划分；
- API 形状；
- 当前 Plan 的实施顺序；
- 临时 workaround；
- 仅仅因为 repository 现在这样写，所以继续这样写；
- 某个技术方案本身。

例如：

> 使用 BVH 加速查询。

这通常是 Impl，而不是 Intent。

除非真正想表达的是更高层目标，例如：

> 查询性能必须优先于实现简单性。

# Intent 不是 Gate

Intent 和 Gate 都可能影响方案判断，但语义不同。

Intent 描述：

> 什么方向更值得追求。

Gate 描述：

> 什么条件必须成立，否则方案不可接受。

例如：

```text
Intent:
保持 drawing 交互尽可能流畅

Gate:
绘制过程中不能出现不可接受的长帧
```

前者提供方向，后者划定边界。

Intent 可以存在模糊性和权衡；Gate 应更接近不可违反条件。

需要显式理解或整理 Gate 时，使用 `gate` Skill。

# Intent 不是 Impl

Intent 不应因为当前已经存在某个实现，就被反向解释成“必须继续这样做”。

区分：

```text
为什么这样设计
        vs
现在恰好这样实现
```

例如：

```text
Intent:
减少模型中的顺序依赖

Impl:
删除 StrokePoint 上的部分属性
```

如果以后找到更好的 Impl，只要仍符合 Intent，就可以替换。

需要判断当前技术选择是否只是可替换手段时，使用 `impl` Skill。

需要把已经明确的 Intent、Gate、Requirement 或高层 Impl 展开成具体实施路线时，使用 `impl-expand` Skill。

# 主动调用

Agent **可以主动调用** `intent`，但只在它能实质改善判断时。

典型场景：

- 用户反复纠正“重点不是这个”；
- 存在多个合理方案，但缺少取舍标准；
- 当前 Plan 很具体，但这些决定为什么存在已经不清楚；
- 架构、数据模型或核心语义将发生变化；
- 现有实现与用户新的方向可能冲突；
- Agent 需要自主做较多技术决定，而不能只靠字面 Requirement；
- 某个看起来像硬约束的要求，可能只是历史实现选择；
- 当前讨论中已经出现明确的设计偏好、优先级或非目标，但还没有被清楚提炼。

不要因为任务涉及软件开发就机械调用。

对于纯机械修改、明确且低风险的局部操作，Intent 通常没有额外价值。

# 提取 Intent

Intent 应优先从用户已经表达的内容中提取，而不是替用户发明。

重点寻找：

- “我更在意……”
- “核心是……”
- “真正的问题是……”
- “我不想……”
- “这个可以牺牲，但那个不能……”
- “以后希望……”
- “现在先不要……”
- “之所以这样，是因为……”

不要把所有这些原句机械收集。

应提炼出少量真正会影响后续决策的内容。

# 不要过度确定

Intent 可以保持在较高层。

不要为了让它看起来完整而补充：

- 未表达的产品目标；
- 未确认的长期路线；
- 假设性的优先级；
- 技术实现偏好；
- 不存在的硬约束。

如果当前 Intent 已足以支持后续判断，就不需要继续细化。

# 允许演化

Intent 不是永久不变的“项目圣旨”。

随着讨论深入，用户可能：

- 改变目标；
- 调整优先级；
- 放弃原有取舍；
- 发现真正问题和最初理解不同。

当新信息明确改变方向时，应更新 Intent，而不是维护历史表述。

但不要因为 Impl 改变，就自动认为 Intent 也改变。

# 输出

默认保持简短。

如果用户只是需要继续讨论或实现，可以在内部使用 Intent，不必强制生成文档。

当需要显式输出时，推荐结构：

## Intent

### Goal
真正希望达成什么。

### Priority
发生冲突时，什么更重要。

### Trade-offs
允许牺牲什么来换取什么。

### Non-goals
明确这次不追求什么。

只保留会影响决策的内容。

# 不要做什么

- 不要把 Intent 写成详细 Requirement；
- 不要把 Impl 冒充 Intent；
- 不要把 Gate 全部复制进 Intent；
- 不要把用户没表达过的偏好补齐；
- 不要为了形式完整而强迫输出 Goal / Priority / Trade-offs / Non-goals 全部字段；
- 不要把 Intent 变成固定流程的第一步；
- 不要因为存在 Intent 就阻止 Agent 正常推进；
- 不要把历史 Plan 当成当前 Intent 的权威来源。

# 核心原则

> **Intent 不是告诉 Agent 必须怎么做，而是告诉 Agent 在做选择时，什么方向更值得保留。**
