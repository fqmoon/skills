# Premise

Premise 是一个一次性的**共同前提对齐命令**。

它不负责 Review，不负责总结整个项目，也不负责重新解释所有代码。

它只回答一个问题：

> **为了让用户现在能够参与当前判断，双方必须先共同知道什么？**

# 目标

Agent 往往刚刚阅读过 repository、diff、测试和调用链，因此持有大量“热上下文”。

用户可能：

- 数周没有阅读当前代码；
- 只记得项目目标和少量高层设计；
- 不记得具体实现、函数名和近期修改；
- 不知道 Agent 当前正在隐式依赖哪些事实。

Premise 的目标不是把所有上下文重新讲一遍，而是恢复当前判断所需的**最小共同前提**。

~~~text
Agent 当前掌握的事实
        ↓
提取当前判断真正依赖的前提
        ↓
恢复双方共同认知
        ↓
再进入 Review / 分析 / 决策
~~~

# 输出内容

优先按以下顺序组织，但不要为了格式完整而机械填充无关内容。

## 1. 当前目标

用 1~2 句话说明：

- 当前正在判断什么；
- 本次改动或讨论试图改变什么。

不要从文件、函数、class 或 API 开始。

## 2. 必要前提

只列出理解当前问题必须知道的系统事实。

这些前提应：

- 可以脱离源码理解；
- 使用普通语言；
- 与当前判断直接相关；
- 尽量少，通常不超过 7 项。

不要恢复整个项目历史。

## 3. 区分前提的层级

必须主动区分：

~~~text
需求 / 不变量
    ↓
设计选择
    ↓
当前实现事实
~~~

### 需求 / 不变量

无论内部怎样实现，都必须成立的东西。

### 设计选择

当前为了满足需求而采用的方案，但理论上可以替换。

### 当前实现事实

repository 现在具体怎样做，例如某个数据结构、缓存方式或调用关系。

不要把“当前代码就是这样写的”误当成“系统必须这样设计”。

## 4. 当前变化

如果当前判断与一次改动有关，用：

~~~text
原来
  ↓
现在
~~~

说明真正发生了什么变化。

不要按 commit、文件或 diff 顺序流水账复述。

## 5. 代码索引

只有在前面的共同前提已经清楚后，才可以列出：

- 模块；
- 文件；
- 关键 symbol；
- 必要的调用入口。

它们只用于后续深入调查，不承担解释系统的主要职责。

# 隐式前提必须显式化

后续结论如果依赖一个重要事实，而这个事实用户未必知道，应先把它说出来。

例如，不要直接说：

> 这里不能只 invalidate 当前 Layer，否则 downstream cache 会 stale。

应先说明：

> 后续 Layer 的累计结果依赖前面 Layer 的输出，因此修改中间 Layer 后，后续缓存也会失效。

然后再给出结论。

如果分析过程中发现新的重要前提，应先补充这个前提，再继续推理，而不是默默把它加入 Agent 自己的上下文。

# 不发明术语

不要为了压缩解释而创建新的项目术语。

优先只使用：

1. repository 中已有的名称；
2. 项目文档已经使用的概念；
3. 常见的软件工程术语。

如果必须描述一个尚未命名的概念，优先使用普通语言直接描述它，而不是替它命名。

已有术语如果用户当前可能不记得，应先用普通语言说明它表示什么。

# 不假设用户记得实现

默认假设用户：

- 知道项目大方向；
- 不记得当前局部实现；
- 不记得最近一个月发生的具体代码变化；
- 不记得函数、文件和调用链；
- 需要先恢复系统关系，才能判断实现细节是否合理。

因此不要使用：

> “这里还是之前的 X 机制”
>
> “和原来的 Y 一样”
>
> “继续走 Z 链路”

除非已经在当前 Premise 中解释 X、Y、Z 是什么。

# 不是 Summary

Premise 不是项目总结，也不是 diff summary。

Summary 倾向回答：

> 发生了哪些事情？

Premise 回答：

> 为了理解接下来的判断，我必须先知道哪些事情？

因此：

- 不追求覆盖面；
- 不列举所有修改；
- 不复述完整实现；
- 不因为某个细节存在就把它带给用户。

只保留会改变当前理解或判断的前提。

# 不是 Up

up 解决的是**当前讨论层级太低**：

> 把问题放回更高、但仍足以回答问题的抽象层。

premise 解决的是**双方推理起点不一致**：

> 把当前判断所依赖、但尚未共享的前提补齐。

两者可能同时有用，但不是同一件事。

~~~text
Up:
“我们是不是讨论得太细了？”

Premise:
“你刚才的结论依赖哪些我可能并不知道的前提？”
~~~

# 不负责 Review

Premise 不主动：

- 找 bug；
- 判断代码质量；
- 给出完整 Review；
- 提出大量修复方案；
- 展开 Implementation Plan；
- 逐文件检查实现。

它的职责在 Review 之前结束。

推荐关系：

~~~text
实现 / 修改
    ↓
Premise
    ↓
双方共享最小必要前提
    ↓
Review / 分析 / 决策
~~~

是否继续 Review，由用户或其他 Skill 决定。

# 核心原则

> **不要假设共同上下文存在。先显式恢复当前判断真正依赖的最小共同前提。**

> **前提对齐后再讨论结论；没有共享的前提，就没有真正共享的判断。**
