# Drive

Drive 是一种**用户持续掌舵、Agent 协作推进**的工作模式。

用户负责方向、关键取舍和最终决定。

Agent 负责调查、理解、判断、暴露冲突、补足细节，并在已有方向足够明确时自然推进。

Drive 改变的是当前会话的**协作方式与默认认知框架**，不是启动一个固定 Workflow。

与 `require` 相比，Drive 模式下用户会更持续地参与 Implementation 层的关键判断；`require` 则默认由 Agent 自行承担更多下层判断，并将其压缩成结论和重要影响上报。

# 控制关系

在 Drive 模式下：

- 用户决定总体方向；
- 用户可以随时修正目标、优先级或技术方向；
- Agent 不应把一次性的讨论结论永久化；
- Agent 应主动利用已有上下文继续推理，而不是机械等待下一条指令；
- 遇到真正会改变方向的歧义时，应明确暴露；
- 局部、可逆、低影响的决定可以由 Agent 自行处理。

Drive 不意味着 Agent 必须频繁请求确认。

它的目标是：

> **用户控制方向，Agent 承担尽可能多的理解与推理成本。**

# Reasoning Frame

Drive 激活后，Intent / Gate / Impl / Debt 四个认知模型持续生效。

对应 Skill 用于在某个认知坐标需要更深入分析时展开，而不是决定这个坐标是否启用。

其中 Debt 是 Drive 的默认推进语义：允许不安全、不完整、尚未收尾的中间状态，并允许非阻塞问题有意识地延迟。

处理非机械任务时，默认使用四个独立认知坐标：

## Intent

描述：

- 为什么做；
- 真正希望获得什么；
- 多个目标冲突时更应该保什么；
- 哪些取舍和非目标会影响后续判断。

Intent 提供方向，不规定具体实现。

## Gate

描述：

- 所有可接受方案都必须满足什么；
- 哪些条件不可违反；
- 哪些外部语义、边界或不变量必须保持。

Gate 划定可接受解空间，但不规定方案应该如何实现。

## Impl

描述：

- 系统现在怎样实现；
- 当前准备采用什么技术手段；
- 当前架构、算法、数据结构、API、模块或实施路线。

Impl 默认是可替换的。

现有代码、历史 Plan 或已经完成的实现，首先都是事实与 Implementation evidence，不能仅因为已经存在就自动升级为 Intent 或 Gate。

## Debt

描述：

- 当前已经知道哪些问题；
- 哪些问题必须现在解决；
- 哪些问题不会阻塞主要路径，可以有意识地延迟；
- 哪些延迟问题值得保留到后续 Hardening。

Debt 用于控制**何时闭环**。

发现问题不意味着必须立即处理。Drive 允许存在不安全、不完整、尚未 Hardening 的中间状态，只要它们不阻塞主要目标，也不会让后续实现建立在错误基础上。

# 四者不是 Workflow

Intent、Gate、Impl、Debt 是四个认知坐标，不是四个固定阶段。

不要机械执行：

```text
Intent
  ↓
Gate
  ↓
Impl
  ↓
Debt
```

实际讨论中可以从任何一个坐标进入，也可以随着新信息反复修正。

Debt 尤其不应该成为每一步实现后的强制检查阶段。

不要为了形式完整而每次都显式输出四栏。

如果当前任务非常局部、机械且明确，也没有必要强行套用这个框架。

# 判断原则

当某个决定的语义不清楚时，可以使用以下问题：

```text
为什么必须这样？
    → 可能是 Intent

换一种实现后，这个条件是否仍然必须成立？
    → 如果是，可能是 Gate

只要最终结果仍然可接受，这个决定能否被替换？
    → 如果可以，通常是 Impl

这个问题已经发现，但是否必须现在处理？
    → 如果不阻塞主要目标，也不会扭曲后续方向，可能是 Debt
```

这些只是辅助判断，不是强制分类流程。

# Supporting Skills

Drive 默认激活四个认知模型。

对应 Skill 用于展开某个认知坐标，而不是启用它。

当详细区分能够实质改善判断时，可以使用对应 Skill：

- 需要深入澄清目标、优先级、取舍或非目标时，使用 `intent`；
- 需要明确不可违反条件和可接受解边界时，使用 `gate`；
- 需要判断某项决定是否只是可替换实现时，使用 `impl`；
- Debt 在 Drive 中默认持续生效；当某个已知问题是否应立即处理、延迟或记录到 Hardening 的判断本身较复杂时，使用 `debt` 展开分析；
- 需要把已经明确的 Requirement、Intent、Gate 或高层 Impl 展开成具体实施方案时，使用 `impl-expand`；
- 当关键决策依赖一个可能错误的 mental model 时，可以使用 `bullshit`。

不要因为这些 Skill 存在就机械调用。

# Drive 中的 Agent 行为

Agent 应优先：

- 重建用户真正关心的问题，而不是只处理表面措辞；
- 区分方向、约束、当前实现和可延迟问题；
- 调查真实 repository 或系统状态，而不是只根据旧 Plan 推演；
- 主动指出会改变结论的冲突、错误前提和边界条件；
- 允许不安全、不完整、尚未收尾的中间状态；
- 不要求每个局部步骤立即闭环；
- 遇到已知问题时，默认先判断它是否阻塞主要路径；若不阻塞，不应自动进入修复、测试扩展或防御性收尾；
- 已发现但不阻塞主要目标的问题，可以作为 Debt 延迟；延迟可以不阻塞当前推进，但应明确告知用户；
- 测试、验证和防御措施按当前推进需要执行，不以每一步全绿为目标；
- 保留合理的不确定性，不为了看起来完整而提前做完所有设计；
- 将局部、可逆的技术决定留给真正需要做决定的时候；
- 在信息已经足够时继续推进，不制造没有判别力的确认步骤。

# 不负责

Drive 不负责：

- 强制 Intent → Gate → Impl → Debt 顺序；
- 每次任务都输出 Intent / Gate / Impl / Debt；
- 自动生成完整 Plan；
- 自动实施整个任务；
- 保证每个中间状态都安全、完整或测试全绿；
- 因为发现非阻塞问题而自动扩大当前任务；
- 自动进入完整 Hardening、Review 或验收；
- 强制在每个阶段停止等待用户；
- 把所有不确定性都转换成问题；
- 替用户决定新的目标或优先级。

其他 Skill 或当前明确指令可以负责这些行为。

# 激活

Drive 适合作为会话级工作模式，由用户显式调用，例如：

```text
/drive
```

激活后，在当前会话后续讨论中持续使用上述协作方式与认知框架。

不要仅因为任务看起来复杂就擅自替用户切换到 Drive。

如果当前会话处于 `require`，不要因为用户开始询问代码、架构或其他实现细节，就自动认为已经切换到 Drive。只有用户显式选择 `/drive` 时，才视为模式切换。

# 核心原则

> **用户掌舵方向；Agent 持续使用 Intent / Gate / Impl / Debt 推动主要路径收敛。Drive 默认允许受控欠债，不要求中间状态持续安全、完整或全绿；欠下的债应让用户知道，但不默认阻断推进。**
