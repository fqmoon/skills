# Up

Up 是一个一次性的**抽象层级提升命令**。

它不切换工作模式，也不改变后续会话的默认协作方式。

调用后，只针对当前正在讨论的问题，重新选择一个更高、但仍足以清楚回答问题的抽象层级。

# 目标

当当前讨论已经陷入：

- API；
- 函数；
- 调用链；
- 文件；
- class / struct；
- 数据结构；
- 具体实现步骤；

而用户真正想确认的是更高层的问题时，主动抬高讨论层级。

优先重新表达：

- 概念是什么；
- 各部分分别属于什么层级、空间或职责；
- 各部分之间是什么关系；
- 边界在哪里；
- 状态或数据如何在几个主要部分之间变化。

# 回答方式

优先使用简单关系描述。

例如：

```text
A 属于 X 空间。
B 属于 Y 空间。
A 通过 Z 转换为 B。
```

或者：

```text
A 负责输入语义。
B 负责渲染语义。
问题发生在 A → B 的边界。
```

如果这样的关系已经足以回答问题，就停止。

不要因为掌握了更多实现细节，就继续向下展开。

# 选择抽象层级

不要机械地只提升一级。

应提升到：

> **能够清楚回答当前问题的最低高层级。**

也就是说：

- 不要停留在无关的实现细节；
- 也不要继续上升到空洞的架构原则或哲学概括。

如果当前问题混杂了多个抽象层，应主动拆开，并指出用户当前真正需要确认的是哪一层。

# 默认忽略的内容

除非它会改变高层结论，否则不要主动展开：

- API；
- 函数名；
- 文件名；
- class / struct；
- 调用链；
- 数据结构；
- 具体实现步骤；
- 调试过程。

实现细节只有在**缺少它就无法确定概念结论**时才保留。

# 不是总结

Up 不是 summary。

不要仅仅：

- 缩短上一条回答；
- 重复已有结论；
- 把细节压缩成更短的细节列表。

应重新判断当前问题所在的抽象层级，并从更高层重新回答。

# 与工作模式的关系

Up 可以在任何工作模式下调用，例如 Drive 或 Require。

它只影响当前这一次回答。

调用完成后：

- 不进入新的模式；
- 不持续限制后续讨论；
- 用户如果继续追问实现，应正常向下讨论。

# 示例

当前讨论：

> A 模块输出的坐标传给 B 后，为什么缩放不对？是不是某个接口转换错了？

调用：

```text
/up
```

应优先回答：

> A 使用 Canvas Space。
>
> B 使用 Render Space。
>
> 两者之间存在一次 Canvas → Render 的空间转换。
>
> 所以当前真正需要确认的是：B 收到的数据是否已经位于 Render Space。
>
> 具体由哪个函数完成转换属于下一层问题。

而不是继续展开接口、函数和调用链。

# 核心原则

> **先把当前问题放回正确的抽象层级，再回答它。**

> **关系已经清楚时停止，不继续下钻。**
