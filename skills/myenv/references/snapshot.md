# 快照生成与维护

快照是用于快速还原个人环境的自描述目录，不是完整镜像，也不要求一键执行。写入前遵守 [隐私规则](privacy.md)。

## 输入与更新依据

用户意图、现场环境和已有快照均可参与生成。明确哪些以现场为准、哪些保留历史偏好、哪些需要重新选择。不要把所有现场差异自动覆盖进快照。

更新前读取已有材料，保护仍有意义的说明与配置。整合多个快照时保留重要来源与选择理由；无法判断的冲突先确认。不因本次范围缩小而自动删除范围外内容。

## 文件格式与组织

- 描述性内容使用 Markdown。
- 静态配置保留软件原生格式与语法，例如 `.conf`、`.yaml`、`.toml`、`.json`；不统一转换成 Markdown 或其他清单格式。
- 配置片段保留原生语法，由配套 Markdown 解释使用方式。
- 如果用户授权生成辅助脚本，采用对应语言的原生格式，说明前提、执行范围和副作用；生成不等于授权执行。

目录结构自由。默认可以按软件组织，紧密关联的内容也可以按用途组合；普通依赖可通过说明关联，不必合并目录。不强制模板、固定目录树或机器可读清单。

## 入口描述

生成目录应有容易找到的 Markdown 入口，通常为 `README.md`，说明：

- 生成时间；更新时区分原始生成与本次更新时间。
- 来源系统、架构以及与还原相关的运行环境。
- 生成目的、包含范围与明确未包含的部分。
- 希望保留的环境偏好与重要版本要求。
- 内容导航、已知限制、待确认和未验证项。
- 已纳入的身份或机器信息类别，以及分享前的提醒。

来源环境信息与目标适用条件分开描述，不因来源系统相同就假定可直接应用。

## 配置与描述的关系

针对相关软件或组合，记录版本选择、安装来源或方式、依赖、期望行为与验证方式。按实际内容区分：

- **完整配置**：目标位置、适用条件、覆盖前需保留的差异。
- **配置片段**：插入位置、合并方法、所依赖的已有内容、避免重复的方式。
- **描述性意图**：希望实现的状态、不能牺牲的偏好、可适配的实现选择。

不要把无法直接使用的片段描述成可整份覆盖的配置。涉及占位符时明确需要补充的值，避免产物看似可用却无法使用。

默认配置可以生成，但优先保留软件版本和非默认定制，不为追求完整性无差别复制配置目录、缓存或日志。

## 检查与报告

检查入口能否找到相关内容、描述与配置是否一致、原生配置语法是否可验证、依赖和应用条件是否足够清楚。不把无法在当前环境验证的内容标为已验证。

报告新增、更新、保留、删除的内容及原因，列出待确认项与隐私处理结果。除非用户授权，不把生成的快照上传、暂存或提交。
