# Gate

Gate 定义**所有可接受方案都必须通过什么**，而不定义方案应该如何实现。

它不是 Plan、Workflow、实现方案或技术设计，而是位于当前问题与可接受结果之间的一组必经条件。

不同方案可以采取完全不同的路径。只要通过相同的 Gate，它们都仍然属于可接受解。

```text
             ┌── Solution A ──┐
Problem ─────┼── Solution B ──┼──► Gate ──► Acceptable Result
             └── Solution C ──┘
```

# 与 Intent / Impl 的关系

Gate 是三个并列认知坐标之一：

```text
Intent:
为什么做、什么更重要

Gate:
什么必须成立

Impl:
当前怎样实现
```

三者不是固定顺序的 Workflow。

Intent 提供方向，Gate 划定可接受解空间，Impl 表示当前选中的实现手段。

需要理解目标、优先级或取舍时，使用 `intent` Skill。

需要判断某个技术决定是否只是可替换实现时，使用 `impl` Skill。

需要把当前 Requirement、Intent、Gate 或高层 Impl 展开为具体实施方案时，使用 `impl-expand` Skill。

# 什么属于 Gate

Gate 记录不依赖具体实现方式、但任何可接受方案都必须满足的条件。

典型内容包括：

- 最终必须具备的能力或行为；
- 无论如何实现都必须成立的需求；
- 不得违反的硬约束；
- 范围边界与明确的非目标；
- 外部可观察的语义；
- 兼容性、保留性等不可丢失的要求；
- 能够区分可接受结果与不可接受结果的条件。

判断一项内容是否属于 Gate，可以问：

> 如果完全换一种实现方式，这个条件是否仍然必须成立？

如果答案是“是”，它通常属于 Gate。

# 什么不属于 Gate

Gate 刻意让 solution space 保持未决。

以下内容通常不属于 Gate：

- 架构；
- 内部抽象；
- class、module 或 manager 的具体划分；
- 为实现方便而选择的 API 形状；
- 任务拆分；
- 实现顺序；
- 技术冲突的提前解决；
- 不同实现模块之间的协调方式；
- 对实现难度的估计；
- 在多个技术可行方案中提前选择一个；
- 仅仅因为当前 repository 结构而产生的实现要求。

这些问题以后可能非常重要，但重要并不意味着它们是 Gate。

# Gate 不负责可行性分析

Gate 不负责证明某个实现方案在当前代码结构下是否可行。

工程可行性应在具体实现、调查或验证阶段处理。

但如果某个外部硬限制会改变问题本身，它仍然属于 Gate 的边界。例如：

- 平台限制；
- 协议保证；
- 兼容义务；
- 法律或外部契约；
- 任何实现都无法绕过的客观限制。

区别在于：

```text
“当前 repository 结构让这个修改很麻烦”
    → 不是 Gate

“目标平台无法提供这个行为”
    → 属于 Gate 边界
```

# Gate 不是 Milestone

Milestone 描述沿某条既定路径已经走到哪里。

Gate 描述的是无论选择哪条路径，都必须满足的条件。

```text
Milestone:
    Implement storage layer
    ↓
    Implement API
    ↓
    Implement UI

Gate:
    User data survives reload
```

前者已经假定实现路线。

后者没有。

# Gate 不是检查流程

Gate 之后可以被用于 Review、验证或验收，但验证过程本身不属于 Gate 的定义。

Gate 只定义通过条件，不规定何时检查、如何检查、由谁检查。

因此，即使实现尚不存在，Gate 仍然有意义。

# 主动调用

Agent **可以主动调用** `gate`，但只在明确可接受解边界会实质改善判断时。

典型场景：

- 多个方案都可行，但必须明确哪些性质不能丢；
- 用户表达了硬约束、不变量或不可接受结果；
- 当前讨论可能把 Impl 误当成不可违反条件；
- 实现或 Review 暴露出原有边界并不明确；
- 后续 Agent 需要较大自主权，但必须知道不能越过什么。

不要因为任务涉及设计或实现就机械调用。

# Gate 的质量

好的 Gate 应该同时满足两个条件：

1. 与具体实现无关；
2. 足以排除明显错误的结果。

太弱：

> 改进 Layer Shader。

它无法区分成功和失败。

太具体：

> 新增 `LayerShaderManager`，并由 layer reducer 保存 WGSL 字符串。

这已经选择了 Impl。

符合 Gate：

> 每个 Layer 独立保有自己的 Shader 状态，并且该状态能够被持久化和恢复。

要求已经明确，但实现仍然开放。

# 核心原则

> **Gate 定义一个方案必须通过什么，而不是这个方案应该长什么样。**

Gate 的目的不是提前消除实现层面的不确定性。

它的目的，是明确那些不能协商的条件，同时刻意保留可以安全推迟到后续阶段的不确定性。
