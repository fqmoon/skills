# Bullshit

`bullshit` 用来验证**当前理解是否可靠**。

它不是教学、科普、总结或普通 review。

它的对象不是代码本身，而是用户当前持有的 mental model：用户认为什么是真的、为什么是真的、哪些东西会导致哪些结果、哪些性质应该保持不变。

核心目标：

> **先找理解里的 bullshit，再决定是否需要解释。**

# 输入 Gate

只有当输入中存在至少一个可检查的当前理解、判断、因果关系、定义或不变量时，才执行检查。

有效输入例如：

- “我理解 X 是因为 A，所以 B 会发生。”
- “我认为这里的速度是 physical speed，因此 zoom 不应该改变它。”
- “我的理解是 A → B → C。”
- “我觉得这个 API 的核心语义是不变量 X。”

以下输入不足以执行：

- 空输入；
- 只有主题，例如“WebGPU”；
- 只有问题，例如“bind group 是什么？”；
- 只有泛化请求，例如“帮我理解一下这个系统”；
- 没有表达用户当前 mental model 的材料。

如果输入不满足要求：

1. **STOP**，不要开始解释主题；
2. 明确指出缺少“用户当前的理解/判断”；
3. 提示用户用一两句话给出当前理解；
4. 给 1–3 个简短示例；
5. 不替用户生成、补全或猜测其 mental model。

推荐提示形式：

> 还没有可检查的 bullshit。先给出你当前的理解，例如“我认为 X 是因为 Y”或“我的模型是 A → B → C”。我检查的是你的理解，不是从头解释这个主题。

# 主动调用

Agent **可以主动调用** `bullshit`，但只在高价值场景下。

主动调用必须同时满足：

1. 用户已经表达了一个明确、可检查的 mental model、假设、定义或因果判断；
2. 当前或下一步的重要决策明显依赖这个理解；
3. 如果这个理解错误，会导致明显错误方向、返工、错误 Gate 或错误实现。

不要因为以下原因主动调用：

- 只是不同意用户观点；
- 用户只是提出事实问题；
- 用户只是要求机械修改；
- 用户表达的是偏好或价值选择，而不是可验证理解；
- 只是发现普通实现 bug；
- 只是想展示更多知识。

主动检查后，如果没有发现实质性问题，不要为了证明调用有价值而制造异议。

# 检查流程

## 1. 重建当前 mental model

先用最少的话提取用户当前真正依赖的命题。

不要扩写，不要替用户补全未表达的前提。

必要时区分：

- 概念定义；
- 因果关系；
- 隐含前提；
- 不变量；
- 边界条件；
- 对系统行为的预测。

## 2. 找最可能出错的地方

优先检查：

- 错误事实；
- 概念混淆；
- 把实现细节误认为定义；
- 因果跳跃；
- 隐含前提不成立；
- 把相关性当因果；
- 忽略关键边界条件；
- 内部命题互相冲突；
- 定义过强或过弱；
- 一个反例就能击穿的理解。

不要为了“全面”而罗列低价值挑刺。

## 3. 反例优先

如果能用一个清楚的反例、边界案例或预测测试击穿某个理解，优先使用它。

例如：

> 如果你的理解成立，那么在 X 情况下应该发生什么？

高价值反例优于长篇解释。

## 4. 提出高判别力问题

如果当前信息不足以判断，不要泛泛追问。

提出能够区分多个竞争解释的问题。

低判别力：

> “这个模块怎么工作的？”

高判别力：

> “如果 zoom 翻倍，这个值按你的定义应该变化吗？”

问题越少越好，只保留会显著改变判断的问题。

## 5. 给出结论

对关键命题使用以下判断之一：

- 成立；
- 基本成立，但有边界条件；
- 部分成立；
- 目前无法判断；
- 不成立。

如果用户的理解基本正确，直接说明，不要强行寻找“平衡意见”。

如果存在问题，指出**最先需要修正的那个理解**。

# 输出

默认保持简短，优先输出三部分：

## Current model

用 1–3 条命题概括用户当前理解。

## Bullshit

只列实质问题：错误、歧义、隐藏前提、反例或冲突。

如果没有发现实质问题，明确写“未发现关键 bullshit”，并说明仍然未知的部分。

## Next check

只有在仍有关键不确定性时，给出最少数量的高判别力问题或验证方式。

# 不要做什么

- 不要一上来从头解释主题；
- 不要把用户没说过的观点塞进其 mental model；
- 不要因为名字叫 `bullshit` 就使用攻击、嘲讽或羞辱用户的语气；
- 不要把普通代码 review 当成理解检查；
- 不要把所有假设都列出来，只检查会实质影响结论的假设；
- 不要追求形式上的反对意见；
- 不要把不确定性伪装成确定结论；
- 不要在缺少可验证 mental model 时继续执行。

# 与其他 Skill 的关系

```text
bullshit
    验证 Understanding / Mental Model

Gate
    定义所有可接受实现必须满足什么

Ownership
    划分方案搜索空间

Implementation
    在约束下寻找可行解

Integration / Review
    检查实现与组合结果
```

`bullshit` 位于 Gate 之前，也可以在 Gate 或 Implementation 暴露新的事实与冲突后再次调用。

它的目的不是替用户理解，而是尽快发现：

> **当前理解中，哪一个错误最可能让后面的所有工作白做。**
