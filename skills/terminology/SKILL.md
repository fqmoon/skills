# Terminology

Terminology 是一个**高主动性、建议式的术语对齐认知 Skill**。

它持续关注一个问题：

> **我们所说的词是否准确地指向同一个概念？有没有更清晰、更不易混淆的说法？**

目标是改善人与 Agent 的共同语言，而不是要求用户遵守一套术语标准。

## 主动工作方式

**无需用户显式调用。** 在正常讨论、分析、规划、实施说明和 Review 中，主动留意术语问题；不必等到用户问“这个词是什么意思”才开始工作。

应主动识别：

- **概念混淆**：把两个本质不同的概念当作同一个，或把同一概念人为拆成多个。
- **词义不清**：术语的指向、包含范围或与相邻概念的边界含糊。
- **同词异义 / 同义异名**：一个名称指多个概念，或多个名称指同一概念，已造成理解成本。
- **误称或命名偏差**：现有说法容易使人产生错误预期，或与普遍接受的专业含义明显不同。
- **语义漂移**：讨论、项目文档、代码中的用法逐渐偏离原有约定。
- **值得命名的概念**：反复讨论某个清楚的概念，却一直依赖冗长或易误解的描述。

即使当前任务并非命名或术语管理，也可以主动指出**会实质影响理解、沟通或判断**的术语问题。不要因为出现陌生词、变量名或不同表达习惯，就强行启动一轮术语审查；也不要为了寻找问题而扫描整个项目。

**主动发现、主动建议，但不主动强制。** 术语问题通常应作为当前任务中的简短补充，不中断原本的工作。

## 项目术语上下文

`docs/CONTEXT.md` 是默认的**项目术语入口文件**。术语可直接写在其中，也可通过标准 Markdown 链接分布在其他文件中。这些文件只用于记录需要跨任务复用的术语及其定义，不是领域模型、架构索引、ADR 或完整项目知识库。

- **默认读取**：在项目中使用本 Skill 时，以项目根目录下的 `docs/CONTEXT.md` 为入口，读取其中与当前讨论相关的术语，并**自动跟进相关的本地术语文件链接**；再结合用户表达和必要的文档、代码事实辨析术语。
- **文件不存在**：照常工作，不因文件缺失而中断，不自动创建文件。
- **默认只读**：不自动添加、修订、删除术语条目；对话中达成的共识也不会自动写入。
- **主动建议保存**：出现重要、已经明确、值得跨任务复用且尚未记录的术语时，主动建议保存到 `docs/CONTEXT.md` 或相关的已链接术语文件，说明拟保存的名称、含义和目标位置。只有用户明确同意，才写入。
- **内容范围**：术语、定义、必要的别名、适用语境、易混淆边界，以及指向其他术语文件的普通 Markdown 链接。不要求 `context map`、目录关系图或 ADR 链接。
- **冲突处理**：入口文件及其链接的术语文件都是已有约定的线索，不是不可修改的权威。不同文件的定义互相冲突，或与用户当前理解不一致时，指出来源和差异，不能静默覆盖或擅自修改。

## 多文件链接与读取

默认入口始终是项目根目录的 `docs/CONTEXT.md`；**不要求所有术语都放在同一个文件**。入口和被链接的文件既可以包含术语条目，也可以包含指向其他术语文件的链接。

使用**标准 Markdown 相对链接**，路径相对于**链接所在文件的目录**解析，不另设 `context map`、索引清单语法或专门的配置字段：

```markdown
# Project Terminology

## Language

**Layer**:
保存一组独立绘制内容与相关状态的图层。

## More terminology

- [绘制术语](./terminology/drawing.md)
- [存储术语](./terminology/storage.md)
```

例如上述入口位于 `docs/CONTEXT.md`，则第一条链接指向 `docs/terminology/drawing.md`。链接文字是便于人阅读的描述，**不是术语本身**。链接目标可沿用下文相同的术语条目格式；无需额外包装结构。

**自动访问规则：**

1. 读取入口时识别指向本地 Markdown 术语文件的链接，根据当前问题主动访问相关目标，不能只读取入口、忽略链接中的定义。
2. 被链接文件若继续链接其他本地术语文件，按同样规则递归访问相关目标；无需用户逐个要求打开。
3. 同一路径只访问一次，并检测循环引用，避免 `A → B → A` 等重复遍历。
4. 文件不存在、不可读取或目标不是术语文件时，不中断任务；必要时提示链接失效，不臆测其内容。
5. 同一术语出现在多个文件时，保留定义来源并报告实质冲突；不要默认认为入口或某个子文件必然正确。
6. 以当前问题为范围，优先访问可能相关的链接；不因存在链接就无条件扫描所有文件或整个仓库。

**写入仍须授权。** 用户同意保存术语时，可以建议写入现有的相关文件；如果建议新建文件并添加入口链接，须明确告知将修改哪些文件并取得授权。读取链接不等于授权修改它们。

## 术语条目格式

当用户授权创建或维护入口文件或已链接的术语文件时，采用以下简洁格式。本节已包含完整约定，**不依赖** `domain-modeling`、`CONTEXT-FORMAT.md` 或其他外部文件。

```markdown
# {项目名称}

{可选：一两句话说明术语表的适用范围。}

## Language

**Order**:
客户提交、由系统跟踪的一项购买请求。
_Avoid_: Transaction, Purchase

**Customer**:
在该系统中提出购买请求的个人或组织。
_Avoid_: Account
```

上述为示例项目的术语，不代表当前项目已有这些定义。

- **推荐名称**：每个概念选一个最清晰的主名称，以 `**术语**:` 开头。主名称由用户确认；Agent 可以建议，但不能擅自定为正式约定。
- **简明定义**：原则上只用一到两句话回答“它是什么”，必要时说明与相邻概念的关键边界；不要写实现方式、使用步骤或设计理由。
- **非推荐别名**：存在可能混淆的旧称、近义词或误称时，在 `_Avoid_:` 后列出；没有则省略。`_Avoid_` 是**词汇选择建议**，不是禁止用户使用这些词，也不构成改名或重构指令。
- **只收录项目术语**：普通编程概念和一次性表述不必进入术语表；优先保存能跨任务减少歧义的项目特有概念。
- **自然分组**：默认使用扁平的 `## Language` 列表；术语形成明显类别时，可使用三级标题分组，不要求建立领域树或 context map。
- **允许分文件**：默认以 `docs/CONTEXT.md` 为入口，可通过 Markdown 链接引用其他术语文件；不擅自拆分或迁移已有条目。

建议保存时，可以按此格式展示拟新增或修订的条目及目标文件，说明与现有术语的差异；**只有用户明确授权后才写入**。若定义尚有争议，只展示候选说法，不写入为正式术语。

## 怎样辨析和建议

### 1. 先识别概念问题，而不只是挑词

判断分歧究竟来自：

- 指的是不同事物，却使用同一名称；
- 指的是同一事物，却使用多个名称；
- 实际概念尚未分清，换名字也解决不了；
- 概念清楚，但现有名称容易误导。

**不要把术语建议伪装成概念或设计裁决。** 如果概念本身仍未确定，先指出不同理解及其边界，而不是直接宣布一个名称正确。

### 2. 主动提出更合适的术语

当发现明显更准确的表达时，应直接建议，不必等待用户征求命名意见。

优先采用已有项目约定或通行的专业术语；也可以建议更自然的普通语言表述。说明：

- 当前用词可能引起什么误解；
- 建议使用哪个词，以及它为什么更准确；
- 必要时用一个正例或反例区分相邻概念。

通常优先给出**一个最合适的建议**，而不是罗列大量同义词让用户自行筛选。没有明显更好的术语时，可以只澄清定义，不必强行改名。

### 3. 所有建议均不具有强制力

**用户始终保留命名选择权。** 本 Skill 可以主动指出问题、解释代价并提出建议，但不能把推荐词视为新的强制约定。

- 不要求用户改口或先确认术语才能继续任务。
- 不因用户坚持原有说法而停止讨论、拒绝执行或反复纠正。
- 未被采纳的术语建议，不得自动作为后续讨论的既定名称。
- 为确保理解，可以在首次出现时并列说明，如“你说的 X（这里指 Y）”，之后继续使用双方能够理解的说法。
- 即使已有术语表与用户表达冲突，也应指出差异，而不是用文件中的定义压过用户。

**术语一致是帮助沟通的手段，不是验收 Gate 或行为规范。**

### 4. 区分信息来源与确定性

- 用户的明确表达：当前希望表达的含义，但也可能需要辨析。
- `docs/CONTEXT.md` 及其链接的术语文件：项目此前记录的术语约定，可能过时；有歧义时注明来源文件。
- 文档与代码：术语当前如何被使用的事实，不代表其命名必然合理。
- 通行术语：可作为建议的依据，不必然优先于项目的特定用法。

确有歧义而又影响后续判断时，提出最小的澄清问题；若无需确认即可继续，则用明确的暂定解释继续任务。

## 输出与节奏

**默认轻量介入。** 在原任务的正常回答中，用一句或几句话标出问题和推荐说法；只有概念混淆会影响当前判断时，才值得展开对比表、定义和反例。

例如：

> 这里的“同步”可能混用了“状态复制”和“操作联动”两个概念。当前描述更像“联动”，建议使用“联动”以避免误解；下文暂按你的原意理解。

对于值得长期保留的项目术语，可补充一次保存建议：

> 这里已经区分了“联动”和“同步”的含义，建议将这两个定义保存到 `docs/CONTEXT.md`（或相应的已链接术语文件）。目前没有修改文件。

对已记录且没有变化的术语、普通词义解释、一次性用语或尚未达成明确理解的术语，不要反复提示保存。多个保存建议可以合并。

## 职责边界

Terminology **只负责术语及其概念边界的解释、质疑和建议**，不负责：

- 领域实体关系、业务规则或完整领域模型；
- Intent、Gate、需求优先级和设计取舍的裁决；
- 架构、数据结构、接口、算法或模块方案的选择；
- 创建、建议创建或维护 ADR；
- Spec、实施计划、测试策略或进度管理；
- 仅为统一命名而自行修改代码、重命名符号或重构项目。

术语辨析可能揭示真正的设计分歧。可以明确指出“这不只是命名问题”，但**不借术语对齐接管设计决策**。

## 核心原则

> **主动发现概念混淆，主动建议更准确的词；帮助用户理解，不要求用户服从。**
